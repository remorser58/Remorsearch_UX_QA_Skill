# Research Protocol

Use this reference for a deep run. The parent skill controls permissions, evidence boundaries, and completion criteria.

## Product framing worksheet

```text
Product/service:
Surface or feature:
Primary user:
Secondary user:
Core job:
Repeated task:
Failure cost:
Trust requirement:
Business constraint:
Technical constraint:
Primary UX question:
```

## Channel selection

Choose channels that reveal different parts of the experience.

| Need | Useful sources | What they reveal |
| --- | --- | --- |
| First-use friction | app reviews, YouTube comments, beginner communities | confusion, onboarding, terminology |
| Repeated workflow friction | expert communities, Reddit, product forums | shortcuts, state loss, missing controls |
| Trust and failure | complaints, consumer forums, support threads | refunds, safety, policy, recovery |
| Content and recommendation | comments, creator communities, review posts | relevance, fatigue, control |
| Local or peer transaction | regional communities, trade boards, chat-related posts | identity, trust, scheduling, disputes |
| B2B workflow | product forums, issue trackers, team communities | permissions, collaboration, automation |
| Product intent | official help, release notes, design docs | intended behavior and constraints |

Do not use a channel only because it is popular. Use it because its users can observe the problem being researched.

## Query expansion

Start with the product and task. Expand through the vocabulary users actually use.

```text
[product] + [task]
[product] + 불편 / 오류 / 실패 / 버그 / 느림 / 복잡
[feature] + 없어짐 / 초기화 / 저장 / 안 보임 / 헷갈림
[product] + 갈아탐 / 탈퇴 / 환불 / 취소 / 추천
[competitor] + 비교 / 차이 / 더 좋은 이유 / 불만
```

After the first pass, add terms found in user language. Preserve spelling variants, slang, abbreviations, and product-specific names.

## Capture record

For each material item, record:

```text
Source URL:
Channel:
Title or thread context:
Published date:
Access date:
Product version or event:
User segment:
Task or situation:
Firsthand / secondhand / unclear:
Relevant text or observation:
Observed behavior:
Stated consequence:
Possible cause:
Contradicting evidence:
Promotion or incentive risk:
Confidence:
```

Keep quotes short and contextual. Do not retain personal identifiers when they do not help the UX analysis.

## Breadth-first pass

1. Scan official product and policy material.
2. Scan at least three distinct reaction or community channels.
3. Search recent and older material when a release or redesign is involved.
4. Separate new-user, active-user, expert-user, and former-user signals when visible.
5. Cluster by task and friction.
6. Deepen only the clusters with repeated or high-impact evidence.
7. Search for counterexamples before writing a strong recommendation.

## What not to infer

- Post volume is not user prevalence.
- Comment emotion is not task frequency.
- A requested feature is not the best solution.
- A competitor's behavior is not proof of fit.
- A current screenshot is not a complete service flow.
- A release-note claim is not proof of user success.
