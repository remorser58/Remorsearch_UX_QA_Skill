# UX/UI redesign (explicit mode)

Use only for an explicitly requested redesign. Standalone research, review, accessibility checks and ordinary QA preserve the existing UI and stack. A redesign does not authorize changes outside its selected screens, publishing, account actions or new infrastructure. Keep PRD decisions, business rules, navigation and data behavior unless an authorized change says otherwise.

## Intent and references

- From the current PRD, actual tasks and available persona evidence, state what must improve and what must stay. Turn each material need into a measurable visual or task check and mark unsupported assumptions; synthetic personas are conditions, not user observations. Include loading, empty, error/retry, success and interrupted/return states where relevant. Use approved synthetic data.
- Study relevant patterns from Mobbin, [UIBowl](https://uibowl.io/landing?lang=ko), Figma Community, Dribbble, Behance and Pinterest. Use [horon-ai/design](https://github.com/horon-ai/design) for design-system patterns and [21st.dev](https://21st.dev/) for landing and intro-page patterns. Stay within the approved time and access/evidence rules. Do not bulk scrape, bypass account/access restrictions, or ingest reference screenshots or private data. Report inaccessible sources instead of guessing.
- Preserve the reference's design intent in an independent reimplementation; refine it for this product. Compare the tasks and state transitions. Break down visual priority, spacing/proportion, alignment, interaction feedback and motion timing. Identify the user-facing advantage, reproduce it with your own components, and refine readability, usability, responsiveness and accessibility against the PRD/persona criteria. Record the source URL, preserved intent, adaptations and why.
- Do not copy protected layouts, code, text, imagery or other assets as a substitute for design. Reuse only when the license and provenance explicitly permit the intended use. Treat the PolyForm Strict Horon repository as analysis-only, with no code or asset import. On 21st.dev verify terms per item, including wrappers and upstream dependencies; a listing is not a blanket license.

## Design and implementation

- Start in the agreed editable Figma baseline; record approved design versions and use the existing Figma gap rule. Plan page hierarchy, component variants, tokens and task/data states. Use the design system and Storybook to specify and inspect component states in isolation, not as a substitute for page QA.
- Implement UI in React in this mode. Use unstyled/headless primitives such as Base UI where compatible; own the styling with shared tokens for typography, spacing, layout and interactive states. Exclude card containers and shadows; group with spacing, type and dividers. Depart only with explicit approval. If the existing stack cannot accommodate React in scope, report the incompatibility and propose options; do not migrate the stack or change the skill runtime. Do not install or add dependencies without authorization.
- Specify motion separately from component visuals (trigger, purpose, duration/easing and fallback). Honor `prefers-reduced-motion`; no task or feedback may depend on animation alone.
- Set a mobile viewport without disabling zoom, handle relevant safe-area insets and edge-to-edge UI, and keep sticky controls usable above system chrome and the keyboard. Check titles, descriptions and canonical/Open Graph metadata where relevant to public sharing; use licensed, approved assets and no private data.

## Visual QA and handoff

Visually inspect the actual authorized build on representative desktop, tablet and mobile widths, including relevant breakpoint edges and orientations. Verify reflow, text clipping, focus/tab order and keyboard operation, touch targets, safe areas, and loading, empty, error and success states. Check light/dark where supported and reduced motion. At each viewport verify what you preserved or changed from the reference and why. Record build, viewport, input, state, findings and what was actually checked; an emulated viewport is not real-device proof. If rendered UI, device, Storybook or a required design surface is unavailable, report that gap, not a pass. Deliver the pattern/decision notes, design-system or implementation changes and scoped evidence with preserved intent; use the existing replay gates for acceptance.
